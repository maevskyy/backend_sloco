# Decisions

Small current decision log. This is not a full ADR system; it is a compact map
of the choices that affect future work.

| Topic | Current Choice | Why |
| --- | --- | --- |
| Product shape | Taste-based city discovery, not Google Maps clone | Recommendations should feel personal, not exhaustive. |
| Backend runtime | Node.js, TypeScript, Fastify | Simple monolith, fast iteration, low overhead. |
| Hosting | Hetzner Ubuntu + Docker Compose + Nginx | More control than PaaS, still simple enough for MVP. |
| Database | Supabase managed Postgres | Avoid DB ops, backups, restores, security, and scaling work during MVP. |
| DB transport | One direct `pg` pool per process against the Supavisor pooler (`SUPABASE_DB_URL`, transaction mode), injected into every store as `Db` (`src/lib/db.ts`); supabase-js only for Supabase Auth (SLO-49). Pool wait > `PG_POOL_CONNECTION_TIMEOUT_MS` or query > `PG_QUERY_TIMEOUT_MS` → 503 + `Retry-After`; per-pool type parsers return PostgREST-shaped values (numeric/int8 → number, timestamps → to_json strings) | Load run 2026-10-03: feed/place-details calls through PostgREST (`feed_fallback_places` etc.) hung 90–273 s with no timeout, and a client disconnect did not cancel them; every PostgREST call also cost an extra ~70–90 ms HTTP hop. Consequences: `instances × PG_POOL_MAX` + other clients must stay under the pooler limit (`../../docs/DEPLOYMENT.md`); saturation answers 503 instead of hanging; side effect — search `isSaved` for logged-in users is now correct, because place ids come back as numbers. |
| Migrations | Add one only when Postgres itself must change (table/column/index/constraint/RPC body); otherwise change the query or app layer | Migrations are permanent, ordered, run-once; the schema should not churn for anything the application can do. See `AGENTS.md` → Migration Restraint Rule. |
| Serving table | `public.places` | One source-agnostic table for TripAdvisor, OSM, and future providers. |
| Geo lookup | PostGIS `geom` + `places_in_bbox` RPC | Efficient bbox queries with GiST index. |
| Map query | Bbox-only, no required `city` | The viewport is the source of truth; avoids city/bbox mismatch bugs. |
| Map density | Backend ranks and limits results | Frontend renders; backend decides what is worth showing. |
| Data imports | Offline mappers + manual Supabase import | Good enough for MVP, keeps provider quirks out of API code. |
| Auth | iOS Supabase Auth SDK + backend JWT validation | Supabase handles sign up/sign in/session; backend owns product APIs and user-owned data. |
| Saved places | `public.saved_places`, `public.saved_collections`, and `public.saved_collection_places` via backend-only APIs | Keeps user-owned data private, supports the iOS Saved tab, and turns saved/collection intent into future recommendation signal. |
| User reactions | `public.place_reactions` keyed by stable `places.source_id`, with the public API still using bigint `placeId` | Reactions survive catalog reimports while the frontend keeps the existing id model. |
| User reviews | `public.place_reviews` (migration `030`), one per user per place, keyed by `(place_source, place_source_id)`; API speaks `placeId`. Tag vocabulary and the 2000-char text limit live in Zod, only `rating 1..5` is a DB check. Invalid input → 422 in this module only. List carries the place card from one join (`count(*) over ()` for `total`). Photos are stage 2 (SLO-70): until then any `photoIds` entry is 422 (SLO-69) | Same reimport-safe key as reactions, but with the source too — `(source, source_id)` is the catalog's unique key, so the card join is exact. A tag added in code needs no migration. 422 is what the iOS spec asks; other modules keep 400. |
| Place photos in details | `GET /v1/places/:placeId` returns both `primaryPhoto` and bounded `photos[]`, hydrated by a second indexed `place_photos` query on cache miss | One details fetch/cached object is simpler than a separate gallery endpoint or RPC rewrite. |
| Feed pagination | `GET /v1/feed/places` takes `offset`; a bigger cached rec snapshot (~100) is hydrated in full and windowed per page, cache key excludes `limit`/`offset`; migration `016` raises both feed RPC caps 50→200 | Deep, stable page-over-page ranking; the RPC-body cap was the blocker, so a migration is the right tool (both personalized and fallback page deep). |
| Map tile density | Per-tile top-N cap by `mapVisibilityScore` (6/10/15/25 by zoom band, uncapped ≥z18; migration `017`), not a global per-zoom score floor; `MAP_TILE_VERSION` bumped to 2 with it | One floor cannot serve cities of different density (Tbilisi z13 235 vs Bucharest 119 over the same floor). A cap is self-balancing: dense areas thin out, sparse ones keep everything, zoom-in only ever reveals more. |
| Map tiles at z≥18 | Same cap as z17 (25), no score floor; `map_tile_min_score` dropped; `map_visibility_score` sorts `nulls last` (migration `029`, SLO-47); `MAP_TILE_VERSION` 4 | The `017` floor at z≥18 dropped places a sparse z17 tile still showed (31 lost around Universitate). A z18 tile is a quarter of its z17 parent under one global order, so an equal cap keeps every parent place; a smaller cap or a floor breaks that, no cap bloats dense tiles. |
| Feed sort | `sort=relevance\|distance` applied in the gateway as a stable re-order of the ranked snapshot before the offset slice; no migration (both feed RPCs already return `distance_m`), no cache-key change | "Nearby" must reorder the recommender's own candidates, not run a different query. Sorting after the recommendation cache keeps one snapshot per user and keeps both orderings consistent page over page. |
| Feed snapshot depth | 200 places per refresh cycle (was 100) | The ceiling both feed RPCs (migration `016`) and the rec-service limit already allowed; a swipe-per-screen feed exhausts 100 in one session. |
| Catalog cities | `GET /v1/cities` reads distinct `places.city` + `country` + count from the pg pool; `name` is the exact feed/`?city=` spelling | No list endpoint existed; hardcoding Kyiv/Bucuresti/Berlin offered empty cities and the wrong Bucharest spelling. |
| Feed `city=` | Hard cut on shown cards (unaccent/case-insensitive). Personalized: gateway post-filter. Fallback: WHERE in `feed_fallback_places` (migration `021`). Unknown name → empty page. Seeds/clusters stay global. | iOS needs "only this city" without throwing away other-city likes that make clusters clearer. A +20 boost leaked Bucharest into later Tbilisi pages. |
| Place details data | Address / hours / phone / website imported from the raw DataForSEO scrape by `cid`, via a staging table + NULL-guarded UPDATE (`TASKS_47`); price from the catalog's categorical `price_level`, maps URI synthesized from the CID | The catalog pipeline dropped these fields, but the raw scrape behind it has them at 100% CID coverage — so no Google Places API spend. NULL-guarded updates keep the import idempotent and never overwrite better data. |
| Category vocabulary | Seven coarse buckets (`cafe, food, bar, culture, nature, shopping, leisure`) defined once in `places/common/place-buckets.ts`, shared by search and feed; matched WORD-BOUNDARY against the venue kind (`primary_type`/`category`) only — never the `types` array | One vocabulary means the client maps its chips once. `types` is an attribute bag (`garden` = "has a terrace"), so matching it filed restaurants under `nature`; word boundaries stop "bar" matching "barbecue restaurant". |
| Search modes | `q` and `category` are independent; either alone is valid. Text = trigram ranking; category-only = browse (nearest-first, no scoring). `radiusMeters` is a hard cut, not a boost | A chip is a browse, not a query. Proximity as a ranking boost could not stop a name match 1 500 km away from winning. |
| Onboarding completion | One `POST /v1/onboarding/complete` writes both halves: picks → `saved_places` (which the feed already counts as favourites) and `profiles.onboarding_status` (upsert, not update). `MeProfile.onboardingStatus` is an API-level enum; the DB column stays free text | One call ends the flow and starts personalization — no separate "interests" store to keep in sync. Upsert because the profiles row may not exist yet (the client can skip `GET /v1/me`), and an update would silently write nothing. |
| Event log | Append-only `events_raw` (facts only, weights applied at read time from `src/config/event-value-weights.json`) + serving receipts `rec_served`/`rec_served_items` written ASYNC by the gateway while the rec-service only prepares them in its response; `request_id` is per SNAPSHOT (pages/sorts share it) and cards carry a stable `position` into it; fallback feeds are not logged (requestId null) | Show↔action joins are the ranker's training data and must be captured at serve time — recomputed scores drift. The gateway owns the pg pool, city/surface/latency and the weights version, so writing there keeps the rec-service DB-free (its canon) and one config in one place. Per-snapshot ids keep the app's impression dedupe and write volume sane under the 10-min feed cache. |
| Recommender parity | The prod engine tracks the research dashboard's DEFAULTS, not a backend-tuned variant: whole-file re-vendor of `backend_recommender.py` (only local deltas = relative imports + the marked dislike/hide extension), zero config overrides, and the dashboard's `text_direct` weights with the OpenCLIP direct-image (photo) channel on (`TASKS_7`) | Two rankers that drift apart cannot be compared, so research findings would stop transferring. Whole-file vendoring keeps the diff auditable; the photo channel is 18 MB of place embeddings covering 91.3% of the catalog and costs no measurable request time. |
| Walk planner | Separate private Python service `walk-planner` (vendored unchanged from the research repo into `services/walk-planner/`), proxied by the gateway module `walks`: generic recursive camelCase↔snake_case key conversion (no field whitelist; CIDs named `sourceId`, `params`/GeoJSON verbatim), service status + error envelope `{error: {code, message, params}}` passed through, `placeId` added to stops/cards/results by one indexed `(source, source_id)` lookup, favourites filled server-side from the feed's own `getUserSignals`; no migration (SLO-67) | The research side owns the algorithm and its golden outputs; a byte-identical vendored copy keeps their acceptance (`golden run --url`, 26/26) valid and updates diffable. No whitelist because edits must send the request echo and sequence back intact, fields a later v1 adds included. Reusing the feed's signal reading keeps walks and the feed personalising alike. 93 % of the Bucharest walk catalog maps to `places`; the rest gets `placeId: null`. |
| Walk planner load control | In the gateway, per process: fixed-window rate limits per user id / client IP (`X-Real-IP` from Nginx) — plan 6/min + 60/h, edits 60/min, search 60/min, place 120/min → 429 `rate_limited`; a semaphore of `WALK_PLANNER_MAX_CONCURRENT` (= the service's load guard, 4) on plan/schedule/insert with ≤ 5 s queue → 503 `busy`; config (10 min) and place screen (1 h) cached in Redis across users, plans/edits never; `sourceId → placeId` not cached. Rollout switched by Repository Variables `WALK_PLANNER_ENABLED` / `WALK_OSRM_ENABLED` (SLO-68) | Starting values of the service's INTEGRATION.md §3.6–3.7. In-process state needs no Redis round trip and is right for one gateway container; with replicas (SLO-27) a key gets N× the limit — move to Redis then. The placeId lookup is one indexed query per response, while a per-id cache would cost one Redis round trip per card. Variables, not a workflow input, so a later unrelated deploy cannot switch the planner off by accident. |
| Backend module architecture | Lightweight layered OOP modules: `controller -> service -> store`, with `index.ts` and `<feature>.module.ts`. All product modules (`map`, `me`, `health`, `saved-places`) migrated; `auth` stays a shared service with its DB call in a store. | Easier to scale than flat Fastify files while staying simple; `saved-places` is the reference implementation. |
| Shared backend code | Split by responsibility — `lib/` adapters, `config/` wiring (incl. `openapi.ts` generator + `http-schemas.ts`), `http/` controller glue. No `shared/`/`utils/` bucket. | Avoids a dumping ground; each piece has an obvious home. |
| OpenAPI source | zod schemas per module, generated to OpenAPI 3.0 components via `config/openapi.ts` | One source of truth; runtime validation and docs cannot drift. |
| API contract | Swagger/OpenAPI | Frontend agents can consume generated contract. |
| Observability | Grafana Cloud + Alloy for now | Fast visibility; self-hosting remains a later cost/control decision. |
| Git flow | User commits and pushes manually | Agents edit and verify, but do not commit/push. |
