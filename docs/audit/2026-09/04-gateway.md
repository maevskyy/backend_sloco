# Аудит dev → main · gateway по модулям

Дата: 2026-09-16 →. Ветка `origin/dev` (прод: образ `dbb1565`) против `main`, 66 файлов кода. Переносится по модулям, каждый — отдельным коммитом, тесты зелёные на каждом шаге. Файлы копируются байт-в-байт (проверка хэшами); правки поверх перечислены явно.

Порядок: places/search → feed → saved-places → onboarding + me → events → cities → доки.

## 1. `places` + `search` (TASKS_44/45/47/48/49, миграции 018–020)

**Что в dev**

- `places/common/place-buckets.ts` — новый. Словарь из 7 «корзин» (`cafe`, `food`, `bar`, `culture`, `nature`, `shopping`, `leisure`) → ключевые слова; это те самые pills. Матчится по границе слова с `primary_type_norm`/`category_norm` — и в SQL (`' '||col||' ' like '% kw %'`), и в TS-двойнике `matchesBucketKeywords` для строк, которые gateway уже держит. `types` (мешок атрибутов Google) сознательно не матчится — там `garden` значит «есть терраса». Казино/adult ни в одной корзине.
- `search`: `q` стал необязательным, добавлены `category` (корзины) и `radiusMeters` — режим «браузинг по категории без текста». Store переведён с PostgREST на прямой `pg` (`getPgPool()`): минус ~100 мс HTTP-хопа на каждый keystroke (TASKS_48). В ответе `query: query.q ?? ""` — чтобы клиентский декодер не сломался на browse-режиме.
- `scripts/integrations/sloco/map.ts`: Берлин → Германия; `google_maps_uri` по CID; **`price_level` из слов** (`inexpensive/moderate/expensive/very_expensive` → 1–4). До этого парсер числовой и молча выдавал NULL — поэтому в проде `priceLevel: null` везде (TASKS_44).
- `scripts/integrations/dataforseo/details-delta.ts` — новый: из сырого скрейпа DataForSEO вытаскивает адрес/часы/телефон/сайт/цену по CID в CSV для staging-импорта (TASKS_47).
- `dumps/place_details_delta.csv` (5 MB, 20 054 строки) и `price_level_backfill.csv` (2 959 строк) — данные для этих бэкфиллов, уже применены к проду.

**Оценка**

- Код аккуратный, комментарии объясняют «почему», тесты есть (`place-buckets.test.ts`, search routes/service). Контракт `/v1/search/places` расширен аддитивно.
- `matchesBucketKeywords` только lowercases, без unaccent — для ASCII-английских `primary_type` это одно и то же; если появятся типы с диакритикой, TS и SQL разойдутся. Сейчас не проблема.
- Комментарий «`nature` и `shopping` почти пустые в двухгородском каталоге» устарел после импорта all-themes (Берлин + sights/shopping) — безвредно.
- **Прямой `pg` в поиске = тот самый пул на 5 соединений** (SLO-32). Решение перейти на прямой Postgres правильное, размер пула — нет.
- **`place_details_delta.csv` оставлен в git сознательно.** Источник — сырой скрейп на SSD Кирилла, у нас его нет: если файл потерять, повторить бэкфилл нечем. 5 MB — цена за воспроизводимость. `price_level_backfill.csv` — то же; проверка, не перезаписал ли он значения, — SLO-13.

**Перенесено:** `src/modules/places`, `src/modules/search`, оба скрипта, `dumps/README.md` + два CSV, `.gitignore` (игнор `dumps/sloco_chunks/`). `package.json`: добавлен скрипт `details:dataforseo`, **`perf:bench` сохранён** (в dev его нет — там нет стенда). Тесты: 155 passed, `tsc` чистый.

## 2. `feed` (TASKS_42/43/46/51/53/54, миграции 019–023)

**Что в dev**

- Query: `sort=relevance|distance` (сорт по расстоянию всего снапшота до нарезки страниц, ранг становится позиционным), `category` (корзины), `city` как **жёсткий срез** («неизвестный город — пустая страница, а не глобальная выдача»). Ответ: `feed.requestId` (id выдачи рекомендера) и `position` у карточки — чтобы клиент клал их в события телеметрии.
- Персональный путь: рекомендер → 200 id → гидрация `feed_places_by_source_ids` (4 аргумента — с 024 работает через default `source`) → **срез по городу/категории уже на гидрированных строках** (`applyFeedCuts`) → пусто → fallback. Это SLO-6, отложено до конца переноса.
- `rec-served.store.ts` — новый: «чек» выдачи в `rec_served` + 200 строк `rec_served_items` (spec 2.2). Пишется после ответа, fire-and-forget с одним повтором, `ON CONFLICT DO NOTHING`. Один SQL-запрос, элементы разворачиваются из jsonb-параметра. Версия весов действий (`config/event-value-weights.json`, `v1_2026-08`) штампуется в каждую строку.
- Сигналы пользователя: список «Been there» — это визит, не предпочтение: место только из него не становится favourite; quick-save определяется по slug `saved` (плюс старые правила — чтобы старые строки не потеряли смысл).
- Тесты: +645 строк service-тестов, +123 routes. Покрыты сорт, срезы, fallback-статусы, чек выдачи, deploy skew (старый рекомендер без `request_id`).

**Оценка**

- Код сильный: контракт расширен аддитивно, каждая ветка объяснена, тесты серьёзные. Из всего dev это самый качественный модуль.
- **Срез после рекомендера** — архитектурная ошибка контракта, а не кода; автор её сам описал в комментарии. SLO-6.
- **Чек выдачи пишет в тот же пул на 5 соединений**, что читают поиск и тайлы: 200 jsonb-строк (~191 KB) на каждую свежую выдачу конкурируют с пользовательскими запросами. SLO-32 п. 3; рост таблицы — SLO-14 (ретеншен через экспортёр рекомендера).
- Кеш рекомендаций — `Map` в памяти процесса, 10 мин, 500 записей. С репликами (SLO-27) у каждой свой кеш: N реплик = N походов в рекомендер на одного юзера. Ключ кеша не знает город/категорию — сегодня это верно (рекомендер их тоже не знает), после SLO-6 ключ обязан их включать.
- Потеря чека логируется `console.error`, а не логгером приложения — в Loki попадёт как неструктурированная строка. Мелочь.

**Перенесено:** `src/modules/feed` целиком, `lib/recommendation-client.ts` (поля чека, все optional — deploy skew), `config/event-value-weights.{ts,json}` (нужен feed'у; сам event log — §5). Тесты: 175 passed, `tsc` чистый.

## 3. `saved-places` + `me` (TASKS_53/54, миграция 023)

**Что в dev**

- Три **системных списка** у каждого пользователя: `saved` (quick-save, default), `favorites`, `been` («Been there»). Создаются лениво при первом сохранении (`ensureSystemCollections`), идемпотентно, с обработкой гонки (`23505` → перечитать) и «усыновлением» пользовательского списка с таким же именем. Удалить системный список нельзя.
- `PUT /v1/me/saved/places/:placeId/collections` — save picker: членство места становится ровно `collectionIds`; пустой массив = unsave. Диф, а не «стереть и записать», чтобы `created_at` у нетронутых списков не сбивался.
- Unsave снимает место со всех списков (иначе закладка «не сохранено», а место в Favorites).
- `/v1/me`: `onboardingStatus` из свободной строки стал enum `not_started | completed | skipped`. В живой БД только эти значения (5 `completed`, 2 `not_started`) — безопасно.

**Оценка**

- Логика продуманная (гонки, усыновление, порядок сохранений). Тесты есть.
- `setPlaceCollections` — три отдельных вызова PostgREST (save, add, remove), **не транзакция**: при падении между ними место может остаться в лишнем списке. Для MVP приемлемо, но это первый кандидат на RPC, когда списки станут важны.
- Rollback 023 нарушает правила своего README — уже отмечено (SLO-16).

**Перенесено:** `src/modules/saved-places`, `src/modules/me`, `config/routes.ts` (константы маршрутов всех новых модулей — просто enum). Тесты: 175 passed.

## 4. `onboarding` + `me` (TASKS_38)

- `POST /v1/onboarding/complete { pickedPlaceIds[≤100], status: completed|skipped }` — сохраняет лайки колоды как обычные `saved_places` (это и переводит юзера на персональную ленту), потом upsert статуса в `profiles`. Неизвестные места пропускаются, не 500. Порядок «сначала лайки, потом статус» — чтобы клиент мог безопасно повторить вызов.
- Оценка: маленький, чистый модуль. Сохранения идут последовательно — по 3–4 запроса PostgREST на место; на 100 лайков это секунды. Для колоды из 10–20 карточек нормально.

**Перенесено:** `src/modules/onboarding` + регистрация в `app.ts`/`swagger.ts`. 

## 5. `events` (TASKS_51/52, миграция 022)

**Что в dev**

- `POST /v1/events` — приём телеметрии батчами (≤ 500 событий, ≤ 1 MiB, иначе 429). Конверт валидируется целиком, события — по одному: плохое отклоняется в `rejected[]`, соседи принимаются. Неизвестные типы **принимаются** с `known_type=false` («новое приложение не должно терять события на старом бэкенде»). Дубли по `event_id` тихо игнорируются. `user_id` — только из токена, из тела игнорируется. Анонимные батчи валидны; невалидный токен — 401.
- Хранение: один INSERT на батч через jsonb-параметр (прямой `pg`), `server_ts` ставит база. Логин «сшивает» историю: `identity_links (anon_id, user_id)`.
- Словарь типов (`KNOWN_EVENT_TYPES`, 24 штуки) и веса действий (`event-value-weights.json`) — это «прайс-лист» для обучения; веса не пишутся в события, применяются при чтении.
- Ретеншен — экспортёр в образе рекомендера (`02-recommender.md` §2), 30 дней.

**Оценка**

- Как код — аккуратно: правила спеки видны в комментариях, границы проверены, ошибки не роняют батч.
- **Как поверхность — открытая на запись точка без rate limit.** Любой клиент без токена может лить 1 MiB / 500 событий на запрос, ограничение только размером тела; в nginx `limit_req` нет. При 30 arrivals/s на бейзлайне сюда мы не били — это отдельная угроза для SLO-32 (тот же пул на 5 соединений) и для диска (`events_raw` растёт до ретеншена). Владельцу безопасности — решить: rate limit в nginx по IP + обязательный `anon_id`, или требовать токен.
- `client_ts` проверяется через `Date.parse`, а в SQL кастуется `::timestamptz`. JS парсит форматы, которые Postgres не примет (`"Tue Sep 16 2026 …"`) — такой батч упадёт целиком с 500, а не отклонит одно событие. Реальный клиент шлёт ISO, так что теоретически.
- Это и есть та самая «аналитика на каждое действие», которую Роман считает избыточной для MVP. Бэкенд её принимает корректно и дёшево (один INSERT); вопрос объёма — к фронту (SLO-22).

**Перенесено:** `src/modules/events`, регистрация в `app.ts`/`swagger.ts`, `openapi.ts` (`okStatus` — 202 для приёма).
